端到端：从问题定义一路做到落地

前面九页教你「每个概念是什么」。这一页把它们串成一条能跑通的路： 从「业务上到底想解决什么」出发，到「模型上线、换成钱」为止，七个步骤每一步都对应到 ai-kb/code 里的真实文件。你照着这条线走一遍，就是一个完整的机器学习实践。

本页要做的三件事

机器学习项目不是「训练一个模型」，而是从业务问题走到落地的一整条流水线。这页把七个步骤画成一个环，每一步都落到真实源码文件上。

目标
把「业务上想解决什么」翻译成「机器能算什么」，再一步步走到可执行的结论。
输出
一张问题定义卡、一份干净的标签、一个训好的模型、一组合乎业务账的圈选名单。
怎么读
先看上面的环记住七个步骤名；再对照「每一步的代码在哪」这张表往下读；最后看「一键复现」把整条流水线跑通。
读完你会知道
顺序比算法重要：把「数据对不对」的验证，放在「模型好不好」的调校之前。

这条七步线，正好把后面 13 个场景页串起来——你看的不是 13 个孤立的坑，是一条流水线上的 13 个关卡：

流水线阶段本库的对应页这一阶段的核心
第 1–4 步：接住问题ch01 从 GLM 出发 · ch02 −1 不是 0 · ch03 频率×损失把业务话翻译成机器话

为什么要按这个顺序排？ 很多项目栽在顺序上：先把模型调得花团锦簇，才发现标签定义本身就是错的（ch02）， 或者训练数据和用模型的那拨人根本不是一回事（ch09）。 顺序的意义在于：把「数据对不对」的验证，放在「模型好不好」的调校之前。

一键复现：把整条流水线跑一遍

下面这些命令在本项目根目录依次执行即可。所有数字都会重新算一遍， 和站点上写的完全一致——因为站点上的每一个数字，都是从 out/facts.json 注入的。

cd ai-kb

python gen_data.py          # 造 20,000 份申请（含「被拒保的人没有出险记录」机制）
python _facts.py           # 抽出唯一数字源 out/facts.json
python test_models.py      # 先验证手写模型的正确性，别在错模型上谈精度
python train_evaluate.py   # 主流水线 step1~step5：读数据→定义标签→切分→四模型→评估
python steps_678.py        # step6~step8：给拒保人打分、算业务账、四种偏差修法对比
python _tune.py            # 反推一套「梯度成立」的核保规则系数
python fig_01_look.py      # 业务侧关键图
python fig_02_model.py     # 模型侧九张图
python _check.py           # 站点自检：七类检查，0 failures
python _build.py           # 生成全部页面 + src/ 源码浏览页
为什么推荐按这个顺序跑？ test_models.py 放在最前面，是因为自己手写模型必须先证明自己没写错—— 不然你调了半天，可能只是在调一个 bug。这一步省不得。
看完这一页，你只需要记住三句话
  1. 机器学习项目是七步环，不是一条直线；数据不行就退回第 ② 步，这是常态。
  2. 真正决定成败的不是第 ⑥ 步（建模），而是第 ② ③ 步（数据从哪来、标签怎么定义）。
  3. 跑完命令序列不是终点，要能回答「这份圈选名单给业务，能省多少钱」——那才是落地。
管理启示

把一个「AI 项目」排进计划时，别按模型复杂度估工期，按七步里最慢的那一步估。 实践里最常拖死项目的从来不是调参，是等数据口径对齐、等标签定义拍板、等业务方确认成功标准。 这三项合起来，通常比写代码多花一倍的时间。

训练集拿来「教」机器的那部分数据，答案一起给它看。
测试集机器从没见过的那部分数据，答案先藏起来，用来检验它是不是真学会了。
特征工程把原始数据捯饬成模型能用的东西：算比率、加标记、分箱、做交互、补缺失。模型好不好，一半看这一步。
超参数不是学出来的，是人提前定好的「旋钮」，比如树最多分几层、学多快。
AUC随机抽一个好人和一个坏人，模型能把好人排得更靠前的概率。0.5 = 瞎猜，1.0 = 完美。
外推（训练域外）给模型一个它训练时从没见过的类型的人打分。它可能装作很懂，其实是在瞎猜。
